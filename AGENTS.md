# CoPod Agent Guide

Canonical instructions for the four CoPod service repositories: `backend/`, `dashboard/`,
`daemon/` and `mail/`. This file is the single source of truth; the sync copies it into
every service repository, so an agent landing in any of them reads the same guide.

Shared agent assets that should exist in every service repository — this guide under
`AGENTS.md`, its Claude Code entry point under `CLAUDE.md`, plus skills and similar under
`.agents/` — are mirrored into each of them by `.github/workflows/sync.yaml`.

`CLAUDE.md` holds a single `@AGENTS.md` import. Claude Code loads `CLAUDE.md` when one
exists and falls back to `AGENTS.md` only when it does not, so the entry point is what
guarantees the guide loads no matter which file the checkout already has. Never point it
at a path outside its own repository: the copies are read in lone clones, CI and agent
worktrees where sibling checkouts do not exist. The sync also commits `.claude` as a
relative symlink to `.agents`, because Claude Code discovers skills under
`.claude/skills/` and other agents use `.agents/`.

## How to use this guide

- This repository is the entry point for agents working anywhere in CoPod. Read this file
  before changing anything, whichever service repository you are working in.
- The guide repository is normally checked out next to the services under one parent
  directory — for example `Projects/CoPod/agents` beside `Projects/CoPod/backend`.
- Read “Shared conventions” below first, then the section for the repository you are in.
- Each service repository's own committed files stay authoritative for its own workflow:
  `README.md`, `.github/workflows/`, `Makefile`, `compose.yml`, `.env.example`,
  `biome.json`, `.editorconfig`. Read them for detail; when one of them changes, update
  this guide to match.
- Change only the guide, the sync workflow and the shared agent assets under `.agents/`
  here. The `AGENTS.md`, `CLAUDE.md`, `.agents/` and `.claude` copies in the service
  repositories are generated by the sync and are overwritten on every run. Product code
  belongs in the service repositories.

## The four repositories

| Directory | What it is | Stack | CI workflow |
| --- | --- | --- | --- |
| `backend/` | cPOD Panel API: the multi-tenant control plane for stateless (PHP) and stateful (Node.js, game servers) workloads | Rust 2024 workspace, Axum, SeaORM, PostgreSQL | `.github/workflows/test.yml` ("Build Test") |
| `dashboard/` | Panel console: accounts, projects, plans, websites, servers, databases, domains and admin; talks to daemon nodes directly for power, console, commands and files | Next.js 16, React 19, bun, Biome, Tailwind 4 | `.github/workflows/test.yml` ("Build Test") |
| `daemon/` | Region-level Kubernetes controller that runs customer workloads | Go 1.26 (module `github.com/copodservices/daemon`), Gin, PostgreSQL | `.github/workflows/push.yaml` ("Push"), plus `docker.yaml` and `release.yaml` |
| `mail/` | Inbound mail server, submission service and webmail | Rust 2024 workspace, SeaORM; static Next.js 16 client in `web/` | `.github/workflows/ci.yml` ("CI") |

All four use `main` as the default branch and run CI on pushes to `main` and on pull
requests.

## Shared conventions

- Never commit or push unless explicitly asked. Do the work, leave it in the working tree
  and report what changed; whoever owns the repository decides when it lands.
- Commit subjects follow Conventional Commits with a scope: `feat(backups): …`,
  `fix(daemon-client): …`, `docs: …`, `chore(docker): …`, `ci: …`.
- Pull requests target `main` and must pass that repository's workflow.
- Never commit secrets or `.env` files; `.env.example` is the template to copy.
- Prefer `rg` for search.
- Run the repository's format, lint and test commands before reporting work as done.
- Keep changes scoped to the crate, package or module you are touching.

## backend — cPOD Panel API

Rust workspace (edition 2024) for the panel. The panel owns accounts, **projects**, plans,
quotas, port allocations, domains and databases, and provisions every workload over the
daemon REST API with a per-node API key. A project is the ownership boundary for every
service: an account owns any number of them, each carries its own plan and quotas, and each
maps to its own `{project-slug}-workloads` namespace on the daemon. Service routes
(`/apps`, `/databases`, `/apps/{uuid}/domains`, `/apps/{uuid}/backups`, …) take the project
from the required `X-Project-Id` header and refuse a request without it, while `/projects`
manages the projects themselves. Browser traffic for power, commands, logs, console
websocket and files goes directly from the dashboard to the node using short-lived,
workload-scoped JWTs minted by `POST /apps/{uuid}/token`; bytes never pass through the
panel. Volume
backups are zip archives of the workload volume kept in `.backups`;
`POST /apps/{uuid}/backups` queues a job (202) that the worker runs in the background.

### Layout

| Path | Contents |
| --- | --- |
| `api` | Axum HTTP surface: auth, projects, apps, domains, databases, admin (`src/routes`) |
| `entity` | SeaORM entities |
| `migration` / `migrator` | Migrations and the one-shot runner |
| `schema` | Request/response DTOs shared with the OpenAPI document |
| `utilities` | Response envelope, RFC 9457 errors, AES-GCM secret storage |
| `daemon` | Typed client for the daemon node REST API |
| `worker` | Health checks, reconciliation, allocations, cleanup |

Integration tests live in `<crate>/tests/`; unit tests sit in `#[cfg(test)] mod tests`
blocks beside the code.

### Commands

```bash
cargo build --all                                          # build every crate
cargo test --all                                           # unit and integration tests
cargo fmt --all --check                                    # verify formatting
cargo clippy --all-targets --all-features -- -D warnings   # lint; warnings are errors
docker compose -f docker-compose-dev.yaml up -d            # Postgres + Adminer
cargo run -p migrator                                      # apply migrations
cargo run -p api                                           # panel API on :3000
cargo run -p worker                                        # background jobs
```

`docker compose up -d --build` runs the full stack from `compose.yml`: PostgreSQL,
migrations once, the default plans (Starter + Unlimited), the bootstrap administrator when
the users table is empty, then the API and the worker. Interactive API docs are at
<http://localhost:3000/scalar>; Adminer is at <http://localhost:8081> (system `postgres`,
user/password/database `cpod`). Compose and the binaries (via dotenvy) both read `.env`.

### Conventions

- `cargo fmt` defaults (4-space indent; no `rustfmt.toml`). Clippy must pass with
  `-D warnings`.
- `snake_case` for functions and modules, `CamelCase` for types,
  `SCREAMING_SNAKE_CASE` for constants.
- Migration files are named `m<YYYYMMDD>_<6-digit sequence>_<slug>.rs`, for example
  `m20261005_000005_backup_jobs.rs`.
- Tests: `#[test]` for units, `#[tokio::test]` for async database tests, descriptive
  `snake_case` names such as `migrates_up_and_down`. Integration tests skip gracefully
  when `DATABASE_URL` is unset, so set it before running `cargo test --all`.

### CI and pull requests

`.github/workflows/test.yml` ("Build Test") runs `cargo fmt --all --check`, clippy
with `-D warnings`, and `cargo test --all` against a PostgreSQL service. PRs target
`main` and must pass it. Describe the behavior change, note validation performed, and
link related issues.

### Configuration and security

Copy `.env.example` to `.env` and fill `JWT_SECRET`, `ENCRYPTION_KEY` and
`ADMIN_PASSWORD`; never commit `.env`. Generate the keys with
`openssl rand -base64 48` (`JWT_SECRET`, signs 15-minute access tokens) and
`openssl rand -base64 32` (`ENCRYPTION_KEY`, AES-256-GCM; it must decode to exactly 32
bytes and protects node API keys and database passwords). The same file covers the
bootstrap administrator, token lifetimes, the PHP runtime images (`PHP_VERSIONS`,
`PHP_RUNTIME_IMAGE_TEMPLATE`), domain ingress (`INGRESS_DNS_TARGET`, `INGRESS_CLASS`),
`POSTGRES_ADMIN_URL` for per-site databases, and dashboard CORS and cookies
(`ALLOWED_ORIGINS`, `COOKIE_SECURE`). `SERVER_PORT` moves the API off `:3000`.

## dashboard — Panel UI

Next.js console for the panel backend: accounts and plans, websites (PHP), container
servers, databases, domains and the administration surface, plus direct daemon access for
power, console, commands and files via short-lived scoped tokens. Bun is the package
manager and runner, Biome owns lint and format, and Tailwind 4 with Radix/shadcn provides
the UI layer.

The console is organised around the **project**: a switcher directly under the sidebar
header picks the active project, and everything a project owns (apps, databases, domains,
email, files, security, metrics, advanced, project settings) sits in a "Project" group that
only appears once the account owns a project. Creating a project is reachable from that
switcher and from `/console/projects/new`. An account with no project at all is redirected
there by `requireProject()`, so every project-scoped screen has a project to act on.

## daemon — region Kubernetes node agent

A region-level Kubernetes controller for arbitrary workloads (custom Docker images,
always-running apps, stateless apps). One daemon runs per region and manages every cluster
in it; replicas are active-active, sharing a PostgreSQL store of workload specs and
coordinating with per-workload leases. The daemon REST API is the only public control
surface. Each workload gets a cluster-internal fs-api Deployment (`{uuid}-fsapi`) that
the daemon proxies file bytes to, so stopping, killing or crash-looping the container
never takes files down. The node address is never public: allocated ports answer on the
node's private address only, and the only externally reachable names are the ingress
hostnames the daemon creates.

### Layout

| Path | Contents |
| --- | --- |
| `cmd/daemon`, `cmd/fsapi` | Entry points for the two binaries |
| `daemon/` | Workload manager, scheduler, leases, power and console logic |
| `environment/kubernetes/` | The only runtime backend (pods, PVCs, ingress, fs-api) |
| `router/` | Gin HTTP API, middleware, websockets; scoped JWTs in `router/tokens/` |
| `internal/` | fs-api server, PostgreSQL store, models, diagnostics |
| `config/`, `system/` | YAML config loading and shared helpers |
| `docs/API.md`, `docs/openapi.yaml` | API reference; `deploy/k8s/` holds manifests |

Tests live beside their packages as `*_test.go`.

### Container paths

The data volume is sized from the workload's `build.disk_space` limit (MiB), and raising
that limit grows the claim on the next apply.

| Path | Contents |
| --- | --- |
| `/mnt/server` | Canonical data volume; the working directory and `HOME`, and the root of the file API |
| `/data` | The same volume mounted again for images that hard-code it (for example `itzg/minecraft-server`) |
| `/mnt/server/public` | Document root served by website runtimes when it exists |
| `/mnt/server/.runtime` | Writable runtime state (nginx temp/pid, PHP sessions and uploads, `/tmp`) |

`invocation` runs through `/bin/sh -lc` in `/mnt/server`; an empty `invocation` uses the
image's own entrypoint.

### Commands

```bash
go build ./cmd/daemon            # control plane binary
go build ./cmd/fsapi             # fs-api sidecar binary
go test ./...                    # unit tests
go test -race $(go list ./...)   # CI parity (race detector)
```

There is no Makefile; container images are built in CI from `Dockerfile.daemon` and
`Dockerfile.fsapi`. Configuration loads from `/etc/daemon/config.yml` (override with
`--config`); `DAEMON_API_KEY` and `DAEMON_JWT_SECRET` come from the environment when not
set in the file.

### API

All `/api/*` endpoints authenticate with `Authorization: Bearer <DAEMON_API_KEY>`.
Per-workload browser routes (power, commands, logs, ws, files) also accept a short-lived,
server-scoped JWT minted by `POST /api/daemons/:uuid/token`. Successful JSON responses
are wrapped as `{"data": …}` (collections add `"meta"`); errors are RFC 9457
`application/problem+json`. `docs/API.md` lists every route.

### Conventions

- Follow `.editorconfig`: tabs, 100-column lines for `*.go`, LF endings, UTF-8, a final
  newline and no trailing whitespace (except Markdown); Markdown, YAML and Nix use
  2-space indents.
- Run `gofmt` and `go vet` before committing. Use standard Go conventions:
  `MixedCaps`, short lowercase package names, documented exported identifiers.
- Keep packages focused (`environment`, `router`, `daemon`). Structured logging uses
  `github.com/apex/log` with `WithField`.
- Tests use the standard `testing` package, named `TestXxx`; CI also runs `-race`. Cover
  state machines, allocation math, token scoping and router behavior when touching
  `environment/`, `router/` or `internal/`.

### CI and pull requests

`.github/workflows/push.yaml` ("Push") builds both binaries and runs `go test $(go list
./...)` and `go test -race` on Linux and macOS. `docker.yaml` builds and pushes images on
`main` and on releases; append `[skip docker]` to a commit for docs-only changes that should
not rebuild images. `release.yaml` publishes tagged releases. Open PRs against `main`,
describe the change, link related issues, and call out API, config or manifest changes.

## mail — inbound mail, submission and webmail

An inbound mail server for `CopodServices`. It accepts SMTP for the domains it owns,
verifies and stores the message in S3, indexes it in PostgreSQL, and hands outbound
submission to a smarthost relay with DKIM signing — it never delivers directly to a
recipient's MX.

- **Inbound** (`:2525` locally, `:25` in production) validates every recipient against a
  local mailbox and refuses unknown ones with 550, so it cannot be used as an open relay.
  On DATA the message is parsed, authenticated (SPF/DKIM/DMARC) and stored. A DMARC
  failure with a rejecting policy is refused with 550; a quarantining policy stores the
  message as quarantined.
- **Submission** (`:2587` locally, `:587` in production) requires AUTH (PLAIN or LOGIN,
  argon2 password hashes), and the envelope sender must match the authenticated mailbox.
  Local recipients are stored; everything else is queued for the relay.
- **Relay worker** claims queued messages, adds a DKIM signature with the sender domain's
  key, and delivers over STARTTLS with retries and exponential backoff.
- **Readers (opt-in)** — with `IMAP_LISTEN` or `POP3_LISTEN` set, a mailbox is also
  readable from another mail app, over implicit TLS when a certificate is configured.

### Layout

| Path | Contents |
| --- | --- |
| `mailcore/` | Config, S3 store, DKIM, SPF/DKIM/DMARC policy, relay client, queue worker, persistence |
| `entity/`, `migration/`, `migrator/` | SeaORM entities, schema migrations, the one-shot runner |
| `server/` | The `mail` binary: SMTP listeners, HTTP API, bootstrap |
| `web/` | Static Next.js 16 client (bun, Tailwind, Radix); `docs/mail-api.md` documents the API contract |

Rust unit tests sit next to the code in `#[cfg(test)] mod tests`; integration tests are in
`server/src/integration_tests.rs`; web tests are in `web/tests/`.

### Commands

```bash
cp .env.example .env   # local configuration
make up                # Postgres, S3 mock, Mailpit
make migrate           # apply migrations (cargo run -p migrator)
make dev               # run the mail service (crate server)
make test              # cargo test --all
make check             # fmt --check + clippy -D warnings (matches CI)
make web-install web-dev web-build web-test   # web client
```

Local ports: inbound SMTP `2525`, submission `2587`, HTTP API `8080` (docs at `/scalar`),
Mailpit UI `8025`, webmail `3002`. The stack is fully offline: Postgres, an
S3-compatible mock, and Mailpit as the relay target. `make help` lists every target.

Run `cargo test --all`; most suites need Postgres reachable at `DATABASE_URL`, so start
`make up` first. Web: `bun test` runs helpers and adapters alone, while the contract suite
needs a live API, for example `MAIL_API_URL=http://127.0.0.1:8080 bun test`.

### Conventions

- Rust uses rustfmt defaults (4-space indent): run `cargo fmt --all` and keep
  `cargo clippy --all-targets --all-features -- -D warnings` clean. Modules and files are
  `snake_case`; types are `CamelCase`.
- The web client uses tabs and Biome (`bun run lint`, `bun run format`); components live
  in kebab-case `.tsx` files.

### CI and pull requests

`.github/workflows/ci.yml` ("CI") runs fmt, clippy and `cargo test --all` against a
PostgreSQL service, builds the API and web images, and runs the web checks
(`bun install --frozen-lockfile`, lint, `bun test`). Pull requests must pass it; describe the
behavior change, link related issues, call out new config or migrations, and attach
screenshots for UI work. Commit subjects follow Conventional Commits with a scope, as in
`feat(web): …`, `ci: …` and `chore(docker): …`.

### Configuration and security

Never commit `.env`. The HTTP API authenticates with `Authorization: Bearer <API_KEY>`;
an empty key disables auth and is for development only. `ENCRYPTION_KEY` must decode from
base64 to exactly 32 bytes — generate one with `openssl rand -base64 32` and never reuse
the development key. The same file sets the listeners (`SMTP_LISTEN` / `SUBMISSION_LISTEN`,
`IMAP_LISTEN` / `POP3_LISTEN`), identity and domains (`MAIL_HOSTNAME`, `MAIL_DOMAINS`), the
seeded postmaster password (`MAIL_BOOTSTRAP_PASSWORD`), limits (`MAX_MESSAGE_SIZE` /
`MAX_RECIPIENTS`), verification (`MAIL_VERIFY_AUTH`), storage and relay (`S3_*`, `RELAY_*`),
and inbound TLS (`TLS_CERT_PATH` / `TLS_KEY_PATH`).
